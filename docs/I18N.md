# EN/FR Localization Pipeline — Task M-04

## What this is

A bilingual (English / French) storefront pipeline for Quebec Bill 96
readiness. It is a technical pipeline, not a legal opinion: whether a
given page, notice, or piece of commercial communication satisfies Bill
96 — including French predominance in Quebec — still needs legal
review. Do not present this PR as "Bill 96 compliant" on its own.

## How locale is resolved

1. The `ecoesse-locale` cookie (`en` or `fr`), set by the EN/FR switcher
   in the header. It lasts one year.
2. Otherwise the `Accept-Language` header: French wins if it appears
   before English, or if English is absent (e.g. `fr-CA,fr;q=0.9`).
3. Otherwise English.

Server components read the locale with `getServerLocale()` (see
`src/lib/i18n/server.ts`); client components use `useLocale()` from
`src/context/LocaleContext.tsx`. The root layout sets `<html lang>`
and the page title/description from the resolved locale, and numbers
on the homepage use `fr-CA` / `en-CA` formatting.

## How to add or change a string

1. Add the key to **both** `src/lib/i18n/locales/en.json` and
   `src/lib/i18n/locales/fr.json`, with the same key path.
2. Run `npm run i18n:check`. It fails if the two files' leaf keys do
   not match exactly, so a missing French translation cannot ship
   silently.
3. Use the string from the dictionary — `dict.section.key` in a
   client component, or `getDictionary(locale)` in a server component.
   Never hardcode a new user-facing string in a component.
4. A missing French key falls back to English at runtime so the UI
   never renders blank — but step 2 is what should catch it first.

## What is translated in this PR

Header, footer, homepage (hero, stats, value section), catalog grid,
product cards, and the cart drawer, plus the site title/description
and the EN/FR switcher itself.

## What is NOT translated yet (next slices)

- Admin dashboard (`/admin`) and the impact certificate page
  (`/impact/[orderId]`) — including the M-03 OG image, whose copy is
  currently English-only.
- Product detail pages.
- Product titles and descriptions. Those are data (seed / Firestore),
  not UI strings, and translating them needs a data model for
  per-locale product fields, not just a dictionary.
- Checkout (Stripe-hosted), emails, and any legal / terms content.

## Why no /[locale] routing in this PR

Moving every route under `[locale]` would have forced a full routing
refactor and conflicted with the open M-03 impact-page PR. The
dictionary, locale resolution, and switcher here are designed to be
reused by a later `[locale]` change without re-translating strings:
at that point the cookie resolution becomes the fallback, and the
dictionaries stay the same.
